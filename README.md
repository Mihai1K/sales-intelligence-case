# Сверка данных как контрольный гейт

**Проверка сказала «сошлось». Данные были неверные.**

📄 [Читать кейс](https://vreklameblogers-max.github.io/sales-intelligence-case/) ·
[Как опубликовать](DEPLOY.md)

---

Система контроля отдела продаж: данные из CRM попадают в аналитическое
хранилище, поверх них считаются метрики и строится ежедневный отчёт
руководителю.

Основной технический сюжет этого кейса — не построение конвейера, а
**обнаружение того, что механизм проверки конвейера не работал**, и замена
его на такой, который ловит ошибки разбора данных.

---

## 1. Проблема

Данные CRM проходят путь `API → raw (jsonb) → нормализация → core → метрики
→ отчёт`. На выходе — цифры, по которым руководитель принимает кадровые
решения: чья выручка, кто не довёл сделку, где потеряны деньги.

Перед приёмкой выгрузки запускалась команда `check`. Она отвечала на вопрос
«всё ли на месте» и возвращала код 0 при успехе.

Проблема в том, что «всё на месте» и «всё правильно» — разные утверждения, а
команда проверяла только первое.

Цена ошибки здесь выше обычной: неверно разобранная запись не выглядит
сломанной. Она остаётся в отчёте, выглядит достоверно, и обнаруживается
через недели — когда кто-то заметит, что цифра не сходится с ощущением.

---

## 2. Причина

`check` сравнивал **количество строк** в исходном слое и в нормализованном:

```python
core_counts = {
    "leads": "SELECT count(*) FROM core.deals",
    "contacts": "SELECT count(*) FROM core.contacts",
    ...
}
diff = raw_count - core_count
ok = diff == 0
```

Отсюда три независимых дефекта:

**Значения полей не проверялись вообще.** Запись, разобранная с неверной
суммой, неверным этапом или неверным ответственным, для такой проверки
неотличима от корректной: она есть, и её посчитали.

**Запросы к `core` не фильтровались по источнику.** `SELECT count(*) FROM
core.deals` считает все сделки, включая демонстрационные. Смешение источников
делало сравнение бессмысленным ещё до того, как дело доходило до значений.

**Изоляция демо-данных была неполной.** Флаг `is_demo` стоял на сделках и
пользователях, но не на компаниях, контактах и задачах. Активности
записывались с жёстко заданным источником `amocrm` независимо от
происхождения:

```python
INSERT INTO core.activities (source, ...) VALUES ('amocrm', ...)
```

То есть демонстрационная переписка была неотличима от боевой прямо в ленте
коммуникаций.

### Как обнаружено

Воспроизведением, а не чтением кода. Взял корректно загруженный набор и внёс
в него семь классов повреждений, **не меняя количества записей**: завысил
суммы у 5 сделок в 10 раз, подменил ответственного у 3, этап у 4, сбросил
признак выигрыша, удалил 2 записи, добавил одну без источника, стёр телефон
контакта.

```
источник  сущность          raw   core  расхождение
demo      contacts           31     31  ок
demo      leads              45     45  ок
demo      users               5      5  ок

код возврата check: 0
```

Проверка сообщила, что расхождений нет.

---

## 3. Решение

### Трёхуровневая сверка

Написал модуль `reconcile`, сравнивающий `core` не с внешним API, а с
дословно сохранённым ответом источника в слое `raw`. Это даёт возможность
сверяться в любой момент, не создавая нагрузки на чужую систему и не завися
от того, что данные там уже изменились.

Три уровня:

1. **Количества** — сколько записей в источнике и сколько разобрано.
2. **Идентификаторы** — какие потерялись при разборе, какие появились в
   `core` без источника.
3. **Значения полей** — 25 правил сравнения по шести сущностям.

Главный уровень — третий. Первые два ловят потерю записей, третий — неверный
разбор, который опаснее: запись на месте, цифра неправильная, по количествам
это не видно.

```python
self._compare(rep, raw, core, {
    "amount":             lambda i: float(i.get("price") or 0),
    "stage_amo_id":       lambda i: str(i.get("status_id")),
    "responsible_amo_id": lambda i: str(i.get("responsible_user_id")),
    "is_won":             lambda i: int(i.get("status_id") or 0) == STATUS_WON,
    "next_contact_at":    lambda i: _ts(i.get("closest_task_at")),
    ...
})
```

### Сравнение с поправкой на типы

Наивное сравнение дало бы расхождение на каждой строке: Postgres отдаёт
`Decimal`, источник — `float`; время приходит в разных часовых поясах.

```python
def _differs(expected, actual):
    if isinstance(expected, float) or isinstance(actual, float):
        # Допуск в копейку: иначе округление даёт ложные расхождения.
        return abs(float(expected) - float(actual)) > 0.01
    if isinstance(expected, dt.datetime) and isinstance(actual, dt.datetime):
        # Один и тот же момент в разных поясах — не расхождение.
        return abs((expected - actual).total_seconds()) > 1
    return str(expected) != str(actual)
```

### Удаление старой команды

`check` не был исправлен — он был удалён. Две команды, отвечающие на один
вопрос по-разному, гарантируют, что на приёмке однажды запустят не ту. Все
ссылки в документации и в скрипте интеграционной проверки переведены на
`reconcile`.

### Изоляция источников

Миграция добавила `is_demo` на все сущности, нормализатор стал принимать
источник параметром вместо жёстко заданной строки. Сверка фильтрует `core` по
источнику.

Проверка результата: полный путь проходит начисто **при живущих рядом
демонстрационных данных** — то есть ровно в той ситуации, что возникнет при
подключении реальной CRM к системе, где уже есть демо.

## 4. Проверка

### Тот же повреждённый набор

```
✓ users        source=5    core=5    missing=0  extra=0  mismatch=0   OK
✓ companies    source=20   core=20   missing=0  extra=0  mismatch=0   OK
✗ contacts     source=31   core=31   missing=0  extra=0  mismatch=1   MISMATCH
    #80001 phone_e164: источник=+7965…4317 core=None
✗ deals        source=45   core=44   missing=2  extra=1  mismatch=16  MISMATCH
    #90001 amount: источник=45000.0 core=450000.00
    #90011 stage_amo_id: источник=143 core=40001
    #90013 is_won: источник=True core=False
    потеряно при разборе: #90021
✗ activities   source=163  core=157  missing=6  extra=0  mismatch=0   MISMATCH

ИТОГ: расхождений 26 — выгрузку принимать нельзя
код возврата: 1
```

Все семь классов повреждений обнаружены, каждый с указанием конкретной записи
и поля. Отчёт выгружается в JSON для автоматической обработки.

### Регрессионные тесты

Каждый класс закреплён отдельным тестом. Важная деталь формулировки:

```python
async def test_wrong_amount_is_detected(loaded):
    await loaded.execute("UPDATE core.deals SET amount = amount * 10 ...")
    deals = _by_entity(await Reconciler(loaded, SOURCE).run())["deals"]
    assert deals.source_count == deals.core_count   # количества сходятся!
    assert len([m for m in deals.field_mismatches if m["field"] == "amount"]) == 5
```

Утверждение `source_count == core_count` стоит в тесте намеренно: оно
фиксирует, что проверка количеств здесь бессильна, и объясняет, зачем нужен
третий уровень.

### Проверка встроена в конвейер приёмки

`make integration-check` прогоняет 12 проверок реальными командами, включая
такую:

```bash
step "сверка ловит испорченные данные"
psql -c "UPDATE core.deals SET amount = amount * 10 WHERE ..."
./scripts/run.sh reconcile --source demo && fail || ok
```

Проверка проходит, только если сверка **завершилась с ошибкой** на
испорченных данных. Механизм контроля сам находится под контролем.

## Побочный результат: усиленная проверка нашла дефект в собственном коде

После расширения сверки на связи активностей она немедленно показала
расхождение на всех 163 записях: `contact_id` в `core` пуст, источник при этом
контакт называет.

Причина: нормализатор не заполнял связь активности с контактом. Лента клиента
`/clients/{id}/timeline` возвращала пустой список для любых данных из CRM,
хотя тесты проходили — в них связь проставлялась вручную.

Исправление изменило `INSERT ... VALUES` на `INSERT ... SELECT FROM
core.deals`. **Это внесло регрессию:** подзапрос при отсутствии сделки
возвращал `NULL` и строка вставлялась, а `SELECT` при отсутствии сделки
возвращает ноль строк и не вставляется ничего.

Обнаружено ревизией собственной правки на фикстуре из пяти сценариев:

```
примечаний на входе: 5   нормализатор отчитался: 5
фактически в core:   4

сделка + контакт + компания        → contact=8001  company=7001
сделка без контакта, с компанией   → contact=None  company=7001
сделка с ДВУМЯ контактами          → contact=8001  ← выбран произвольно
сделка без контакта и компании     → contact=None  company=None
сделки не существует               → ⚠️ ЗАПИСЬ ПОТЕРЯНА
```

Счётчик отчитывался об успехе при молчаливой потере данных.

Два вывода, оба практические. Первый: 257 проходящих тестов не поймали ни
пустую ленту, ни регрессию — тесты проверяли то, что я в них заложил, а не
соответствие данных источнику. Второй: обе ошибки нашёл именно механизм
сверки, ради которого всё и делалось.

## Другие технические решения проекта

### Разделение сторон разговора без машинного обучения

Задача: в записи звонка отличить реплики продавца от реплик клиента. Штатное
решение — модель диаризации (pyannote, WhisperX), требующая GPU, весов и
принятия лицензионных условий.

Перед этим проверил, не пишет ли телефония стороны в разные каналы. Проверки
на `channels == 2` недостаточно: многие записи — моно, продублированное в две
дорожки.

Измерение вместо предположения: разность каналов через `volumedetect`.

```python
"[0:a]channelsplit=channel_layout=stereo[l][r];"
"[l][r]amix=inputs=2:weights=1 -1[d];[d]volumedetect"
```

Результат на сгенерированных образцах: настоящее стерео даёт разность
**−24.1 дБ**, продублированное моно — **−91.0 дБ**. Порог: −60 дБ.

Если телефония пишет два канала, разделение получается точным, а не
вероятностным, и стоит ноль.

Роли каналов при этом **не назначаются автоматически**: какая дорожка
принадлежит продавцу, зависит от оборудования. До подтверждения реальной
схемой обе помечены `unknown` — перепутанные роли меняют оценку продавца на
противоположную.

### Источник тендерных данных: исследование вместо предположений

Требовалось собирать закупки с двух площадок.

**Площадка А.** Страница закупки — JS-приложение, данных в HTML нет. Через
инспекцию сетевых запросов нашёл публичный REST: `main-view`, `positions`,
`companies/public/list/base`. Что доступ действительно публичный, а не
унаследован от сессии браузера, подтверждается соседним запросом чатов,
отвечающим 401 — авторизация работает там, где она есть.

Инкрементальность — через `sitemap` с `lastmod`: обход идёт с последнего файла
и прекращается на первом полностью устаревшем.

Измерение, изменившее модель отбора: на 12 свежих закупках подряд стартовые
цены опубликованы **у одной**. Фильтр по бюджету, обычно первый в тендерном
мониторинге, применим к 8% потока. Поэтому закупка без цены не отбрасывается,
а получает отдельный класс `REVIEW`, а объявленный бюджет и посчитанная нами
оценка хранятся в разных полях — чтобы оценка не выдавалась за факт.

**Площадка Б.** В `robots.txt`, блок `User-agent: *`:

```
Disallow: *f_keyword=
Disallow: *search=
Disallow: /app/next/search-tender/
```

Ровно то, что требовалось автоматизировать, запрещено владельцем. Плюс
`fingerprint2.min.js` на страницах — автоматический доступ отслеживается.
Адаптер не писал; вместо этого подготовил документ с семью вопросами для
запроса официального доступа.

### Защита от записи в чужую CRM

Ошибочная запись в CRM необратима: удалить полторы тысячи примечаний из
карточек задним числом нельзя.

Три независимых уровня, снять нужно все три:

```python
def check_write_allowed(mode, method, path):
    if method.upper() not in WRITE_METHODS:
        return
    if mode is AmoMode.READ:
        raise AmoWriteBlocked(...)
    if not settings.amo_write_enabled:
        raise AmoWriteBlocked(...)
```

Проверка стоит в единственной точке выхода наружу, а не в местах вызова: любой
новый код упрётся в неё автоматически, даже если автор о запрете не знал.

## Что в этом кейсе сделано не кодом

Честные границы:

**Интеграция с CRM проверена только на заглушках.** Полный путь `разведка →
20 записей → нормализация → сверка` пройден на `respx`-моках, артефакты
сохранены. Доступа к реальному аккаунту на момент написания нет. Это
mock-verified, не production-verified, и в документации помечено именно так.

**Диаризация исследована, но не внедрена.** Сравнение вариантов сделано по
документации проектов, замеров производительности на собственном железе нет.

**Воркфлоу n8n сгенерированы, но в production не запускались.** Аудит нашёл в
них 38 замечаний — ни у одной HTTP-ноды нет `retryOnFail`, `onError` и
`timeout`. Зафиксировано как долг, не исправлено.

**Развёртывания не было.** `docker-compose.prod.yml` валиден, но на сервере не
разворачивался.

### Что сделало бы кейс сильнее

- **Замер производительности диаризации** на реальных телефонных записях
  (8 кГц, сжатие) вместо сравнения по документации. Публикуемые метрики
  снимаются на чистой речи и к телефонии применимы плохо.
- **Property-based тесты** для нормализатора: сейчас проверяются
  сконструированные случаи, а генератор входных данных нашёл бы регрессию с
  потерей строк раньше, чем ревизия.
- **Нагрузочный прогон** конвейера на объёме, сопоставимом с реальным
  аккаунтом, — чтобы увидеть поведение под лимитом 7 запросов в секунду, а не
  предполагать его.
- **Мутационное тестирование** сверки: внести дефекты в сам `reconcile` и
  убедиться, что тесты падают. Сейчас проверено, что сверка ловит порчу
  данных, но не проверено, что тесты поймают порчу сверки.


## Запуск

Система полностью работоспособна без внешних доступов — на детерминированном
демонстрационном наборе, который проходит тот же конвейер, что и боевые
данные.

```bash
cp .env.example .env
make build && make up && make migrate
make demo-data
make demo-report
```

Проверки:

```bash
make test               # 257 тестов
make lint
make integration-check  # 12 проверок реальными командами
make security-check     # 15 проверок значений по умолчанию
```
